Docker-MySQL数据持久化迁移

迁移背景

原有环境

在学习 Docker 和 MySQL 时，我们使用 VMware Workstation 创建 Ubuntu 20.04 虚拟机，并在 Ubuntu 中通过 Docker 部署 MySQL 5.7.25。

同时，在 Windows 宿主机上安装 Navicat，通过虚拟机 IP 和 Docker 映射端口连接 MySQL。

原来的 MySQL 部署方式

最初按照教程，在 Ubuntu 的 /tmp 目录下创建 MySQL 数据目录：

mkdir mysql
cd mysql

然后启动 MySQL：

  -v $PWD/conf:/etc/mysql/conf.d \
  -v $PWD/logs:/logs \
  -v $PWD/data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=123456 \

由于启动命令是在 /tmp/mysql 中执行的，因此实际挂载关系为：

├── conf/
├── data/
└── logs/

其中：

  • conf：用于存放 MySQL 配置文件。
  • data：用于保存 MySQL 数据库文件。
  • logs：预留的日志目录。

需要注意，/logs 并不是 MySQL 默认的全部日志存放位置，是否真正向该目录写入日志取决于 MySQL 配置。

遇到的问题

在关闭并重新启动 Ubuntu 虚拟机后，发现原来位于 /tmp/mysql 下的文件出现丢失或被重新初始化的情况。

虽然 Docker 中仍然能够看到 MySQL 容器，但是容器启动后，数据库中只剩下系统数据库：

1

SHOW DATABASES;

返回：

1
2
3
4

information_schema
mysql
performance_schema
sys

这说明当前数据库实例中没有看到之前的业务数据库。

造成该问题的重要风险因素是：MySQL 数据被保存在 **/tmp** 临时目录中。

Linux 的 /tmp 主要用于保存临时文件。不同系统可能通过启动清理机制或定期清理服务删除其中的文件。

因此，不适合将需要长期保留的数据库文件依赖于 /tmp 目录。

需要说明的是：这次未能通过日志完全证明旧数据丢失的唯一原因就是 /tmp 清理，但这种目录选择确实存在数据丢失风险。

为了避免再次出现类似问题，决定将 MySQL 的数据目录从：

1

本次迁移需要满足以下要求：

  1. 保留原来的 MySQL 5.7.25 版本。
  2. 保留 3307:3306 端口映射。
  3. 保留原有数据库数据。
  4. 保留 Windows Navicat 连接方式。
  5. 配置 Docker 自动重启策略。
  6. 保留旧容器和原始数据，以便迁移失败时回退。
  7. 验证容器重启后数据不会丢失。

Docker数据持久化原理

为什么需要数据持久化

Docker 容器具有相对独立的文件系统。

如果数据库文件只保存在容器的可写层中，删除容器时，这些文件也可能随容器一起被删除。

因此，部署数据库时通常需要使用数据持久化机制。

Docker 常见的数据持久化方式包括：

  • Bind Mount：将宿主机指定目录挂载到容器内部。
  • Volume：使用 Docker 管理的数据卷。

本次采用的是 Bind Mount（绑定挂载）。

Bind Mount的工作原理

Docker 启动参数：

1

-v /opt/mysql/data:/var/lib/mysql

表示将 Ubuntu 中的：

1

/opt/mysql/data

挂载到 MySQL 容器中的：

1

/var/lib/mysql

因此：

1
2
3
4
5
6
7
8

MySQL 容器
    │
    │ 写入 /var/lib/mysql
    ▼
Docker Bind Mount
    │
    ▼
Ubuntu /opt/mysql/data

当 MySQL 在容器内部创建数据库或表时，相关数据库文件会写入 Ubuntu 的 /opt/mysql/data。

这样即使容器停止、重启，或者在正确操作的前提下重新创建容器，数据文件仍然保存在 Ubuntu 中。

注意：持久化不等于备份。

如果 Ubuntu 虚拟磁盘损坏、数据文件被误删除或者数据库本身发生损坏，Bind Mount 不能保证恢复数据。

为什么选择 /opt/mysql

Linux 常见目录的用途：

目录 常见用途
/tmp 临时文件
/opt 第三方应用及其相关文件
/var/lib 应用程序持久化状态数据
/home 普通用户个人文件
/etc 系统和服务配置文件

本次选择 /opt/mysql，主要是为了让 MySQL 的配置、数据和日志集中存放，便于学习和管理。

在正式生产环境中，也可以根据系统规范选择 /var/lib/mysql、Docker Volume 或专用数据磁盘。

迁移前检查

检查磁盘空间

迁移时需要同时保留旧数据和新数据，因此必须先确认 Ubuntu 有足够的磁盘空间。

执行：

1

1

1

210M    /tmp/mysql

说明剩余磁盘空间足够完成本次迁移和备份。

1

/tmp/mysql/logs -> /logs

说明原容器确实使用 /tmp/mysql 进行绑定挂载。

检查 MySQL 镜像和容器配置

其中：

  • Network=bridge：使用 Docker 默认桥接网络。

注意：Docker 的 bridge 网络与 VMware 的 NAT 网络不是同一个概念。

本次需要保留 MySQL 镜像版本和自动重启策略。

迁移前备份

为什么迁移前必须备份

本次迁移涉及 MySQL 数据文件的复制和 Docker 容器重建。

如果复制过程中发生错误，或者新容器无法正常启动，就可能影响数据库使用。

因此，正式迁移前至少保留两类信息：

  1. Docker 容器原始配置。
  2. MySQL 数据库逻辑备份。

此外，本次还保留原容器及 /tmp/mysql 原始数据目录。

创建备份目录

执行：

1

mkdir -p /opt/mysql-backup

该目录用于保存本次迁移的备份文件。

备份 Docker 容器配置

执行：

1

docker inspect mysql > /opt/mysql-backup/mysql-inspect.json

该命令会将容器配置保存到 JSON 文件中。

可以检查：

1

ls -lh /opt/mysql-backup/mysql-inspect.json

本次生成的文件大小约为 9.6 KB。

注意：docker inspect 的输出可能包含数据库环境变量和密码等敏感信息，不要将完整文件上传到公开博客或代码仓库。

备份 MySQL 数据库

执行：

1
2
3

docker exec mysql sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --all-databases --routines --events --triggers --single-transaction' \
  > /opt/mysql-backup/all-databases.sql

参数说明：

参数 含义
mysqldump MySQL 逻辑备份工具
--all-databases 导出全部数据库
--routines 包含存储过程和函数
--events 包含事件
--triggers 包含触发器
--single-transaction 对支持事务一致性读取的表进行一致性备份

执行时出现：

1

mysqldump: [Warning] Using a password on the command line interface can be insecure.

这是 MySQL 对命令行密码使用方式的安全提醒，不代表备份失败。

在正式生产环境中，应采用更安全的凭据管理方式，并根据数据库规模、存储引擎和业务写入情况设计备份方案。

检查数据目录权限

执行：

1

ls -ld /opt/mysql/data

本次输出显示目录所有者和所属组均为：

1

systemd-coredump

这是 Ubuntu 宿主机对容器内部 UID/GID 的名称解析结果，不代表 MySQL 数据目录必须属于一个叫 systemd-coredump 的用户。

由于使用了 cp -a，原有文件的数字 UID/GID 已得到保留。

不要为了方便直接执行 **chmod -R 777 /opt/mysql/data**。

随意修改数据库文件权限可能导致 MySQL 无法启动，也会降低系统安全性。

恢复MySQL配置文件

发现的问题

复制完成后，执行：

1

返回：

1

说明新目录中没有找到原来使用的 my.cnf 文件。

需要注意：cp -a 已经成功复制原目录内容，因此该问题不一定是复制失败，也可能是复制前原目录中就没有这个文件。

创建配置文件

执行：

1

vi /opt/mysql/conf/my.cnf

写入：

1
2
3
4
5

[mysqld]
skip-name-resolve
character_set_server=utf8
datadir=/var/lib/mysql
server-id=1000

在 Vim 中：

  1. 按 i 进入编辑模式。
  2. 输入配置内容。
  3. 按 Esc。
  4. 输入 :wq 并回车保存。

配置说明

1. skip-name-resolve

1

skip-name-resolve

禁止 MySQL 在连接认证时进行 DNS 主机名解析。

这可以减少某些 DNS 解析带来的延迟，但需要注意账户授权中主机名与 IP 地址的匹配问题。

2. character_set_server=utf8

1

character_set_server=utf8

设置 MySQL 服务器默认字符集。

在 MySQL 5.7 中，utf8 通常指 utf8mb3，并非完整的四字节 UTF-8。

如果是新项目，通常更推荐使用 utf8mb4。但本次属于原版本数据迁移，因此先保留原有配置，避免同时引入额外变化。

3. datadir

1

datadir=/var/lib/mysql

指定 MySQL 容器内部的数据目录。

由于 Docker 已经进行绑定挂载：

1

/opt/mysql/data → /var/lib/mysql

所以数据实际上保存在 Ubuntu 的 /opt/mysql/data。

4. server-id

1

server-id=1000

设置 MySQL 服务器 ID。

它通常用于 MySQL 复制相关配置。当前仅作为原配置保留，并不表示已经启用了 MySQL 主从复制。

检查配置文件

执行：

1

cat /opt/mysql/conf/my.cnf

确认配置内容正确。

保留旧容器并创建新容器

为什么不能直接修改旧容器挂载目录

Docker 容器创建时，Bind Mount 的挂载关系已经确定。

不能通过普通的 docker start 或 docker restart 命令，将旧容器的挂载源路径直接改为 /opt/mysql。

因此，本次采用以下方案：

1

4

    ↓
停止并重命名
    ↓
mysql-old

新建容器 mysql
    ↓
挂载 /opt/mysql

这样既能保留原容器，又可以创建使用新目录的 MySQL 容器。

禁用旧容器自动重启

执行：

1

docker update --restart=no mysql

这样可以防止旧容器在 Docker 服务重启时自动启动并占用 3307 端口。

1

docker rename mysql mysql-old

此时旧容器没有被删除，原始数据仍然保留在 /tmp/mysql。

  -e MYSQL_ROOT_PASSWORD=123456 \
  --restart unless-stopped \
  -d \
  mysql:5.7.25

参数说明：

参数 作用
--name mysql 设置容器名称
-p 3307:3306 映射 Ubuntu 端口到容器端口
-v /opt/mysql/conf:/etc/mysql/conf.d 挂载配置目录
-v /opt/mysql/logs:/logs 挂载日志目录
-v /opt/mysql/data:/var/lib/mysql 挂载数据库文件目录
-e MYSQL_ROOT_PASSWORD=123456 设置新初始化数据库时的 root 密码
--restart unless-stopped 设置容器自动重启策略
-d 后台运行
mysql:5.7.25 指定 MySQL 镜像版本

这里有两个注意事项。

第一：继续使用 MySQL 5.7.25。

本次复用的是 MySQL 5.7.25 的数据目录，不能直接将同一份数据目录挂载到 MySQL 8.0 容器中尝试升级。

跨大版本升级需要按照 MySQL 官方支持的升级路径执行。

第二：MYSQL_ROOT_PASSWORD 不会修改已有数据库密码。

如果挂载的数据目录已经完成初始化，MySQL 镜像通常不会重新初始化数据库，也不会根据该环境变量重设已有 root 密码。

因此，复用原数据目录时，应继续使用数据库中原有的账号密码。

另外，本次新容器没有继续使用原命令中的 --privileged。MySQL 一般不需要该参数提供的广泛宿主机权限。

实际使用时，应避免把真实数据库密码直接写入公开笔记或代码仓库。

MySQL启动日志出现skip-name-resolve警告

日志中出现类似：

这是因为配置文件中存在：

该参数会禁止 MySQL 使用 DNS 解析客户端主机名。

如果 MySQL 权限表中存在使用主机名的授权记录，可能出现相关警告。

本次 MySQL 已经正常启动，root 登录和 Navicat 连接也都成功，因此暂时没有因为这些警告修改配置。

但在实际项目中，应检查账户的 Host 配置，确保账户权限和连接来源匹配。

MySQL启动日志出现复制线程警告

1

Failed to start slave threads for channel ''

这说明 MySQL 启动时尝试启动复制线程，但未能成功。

为了检查当前是否存在 MySQL 从库配置，进入 MySQL 执行：

返回：

1

说明当前没有通过该命令查询到已配置的从库复制关系。

需要注意：

MySQL 主从复制与 Redis 主从复制是两个完全不同的功能。

Redis 的主从复制配置不会直接导致 MySQL 出现复制线程警告。

为什么不直接删除旧容器

迁移时将旧容器：

1

mysql

重命名为：

1

mysql-old

这样可以保留原始容器配置。

如果新容器出现问题，可以在确认数据状态并停止新容器后，考虑使用旧容器进行回退。

但是需要注意：旧容器使用的是 /tmp/mysql 数据目录，新容器使用的是 /opt/mysql。

迁移后在新容器中写入的数据，不会自动同步回旧目录。

因此，回退时不能假设两份数据仍然相同。

为什么不立即删除 /tmp/mysql

虽然已经完成迁移，但原始目录仍然具有回退和排查价值。

因此，本次迁移完成后，暂时保留：

1
2

/tmp/mysql
/opt/mysql-backup

以及旧容器：

1

mysql-old

待确认新容器长期运行正常、备份可恢复并且不再需要回退后，再决定是否清理。

清理前必须再次确认目标路径，避免误删 /opt/mysql/data。

总结

本次迁移的核心目标，是解决 Docker MySQL 数据存储在 Ubuntu /tmp 临时目录中所带来的持久化风险。

最终完成了以下操作：

  1. 检查 Docker MySQL 原有配置和挂载目录。
  2. 确认 Ubuntu 磁盘空间足够。
  3. 使用 mysqldump 导出数据库。
  4. 使用 docker inspect 保存原容器配置。
  5. 正常停止 MySQL 容器。
  6. 使用 cp -a 将数据从 /tmp/mysql 复制到 /opt/mysql。
  7. 检查新旧数据目录是否一致。
  8. 恢复 MySQL 配置文件 my.cnf。
  9. 禁用旧容器自动重启，并重命名为 mysql-old。
  10. 创建新的 MySQL 5.7.25 容器。
  11. 将 /opt/mysql 作为新的绑定挂载目录。
  12. 检查 MySQL 启动日志和数据库登录。
  13. 创建测试数据库 persistence_test。
  14. 重启容器并确认测试数据仍然存在。
  15. 使用 Windows Navicat 验证远程连接。

最终结果：MySQL 数据已经成功迁移到 **/opt/mysql/data**，容器重启后测试数据仍然存在，Windows Navicat 也能够正常连接并查看数据库。

本次操作也说明了几个重要知识点：

  • Docker 容器不等于虚拟机。
  • Docker 容器内部目录与 Ubuntu 宿主目录可以通过 Bind Mount 建立映射。
  • 数据库不能依赖 /tmp 等可能被清理的临时目录保存长期数据。
  • 迁移数据库时，应先备份、再停止服务、再复制文件。
  • 数据持久化与数据备份是两个不同的概念。
  • Docker 容器可以重新创建，但必须确保数据目录、镜像版本、配置和权限兼容。
  • 迁移完成后，需要通过真实的数据库写入、重启和查询验证结果。

补充： MySQL 5.7 已结束官方维护。本次继续使用 5.7.25 是为了保持与原学习环境兼容。如果以后部署正式项目，应规划升级到仍受支持的 MySQL 版本，并使用独立数据库账户、强密码、最小权限及定期备份机制。
